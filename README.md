# AuraIA: A Next-Generation Cognitive AI Partner for VS Code

![AuraIA Logo](assets/AuraIA_logo.jpg)

AuraIA is not just another AI assistant; it is a sophisticated, privacy-first cognitive architecture designed to serve as a true coding partner. Built with a clear vision and a defined personality, AuraIA aims to provide developers with a calm, insightful, and supportive assistant that deeply understands the context of their work.

At its core, AuraIA operates on a multi-layered model routing system inspired by dual-process cognitive theory ("System 1" and "System 2" thinking). This allows it to be both incredibly fast for simple tasks and deeply analytical for complex ones, ensuring a fluid and intuitive developer experience. All of this is achieved with a local-first approach that respects user privacy, keeping your code on your machine by default.

## The AuralA Persona: Your Calm Coding Partner

Unlike generic AI tools, AuraIA is engineered with a distinct personality. As defined in its core vision, the persona is:

- **Calm and Supportive:** Engages with a professional, warm, and human-centric tone.
- **Insightful and Factual:** Provides clear, empathetic, and jargon-free explanations.
- **A True Partner:** Helps developers reason, create, and refine with confidence, acting as a supportive peer rather than just a tool.

This persona is primarily brought to life by a dedicated `Conversational Agent` (powered by models like `gemma3:12b`), ensuring that all user-facing communication is polished, natural, and helpful.

## The AuralA Cognitive Architecture

AuraIA’s standout feature is its advanced, multi-layered cognitive architecture, which intelligently orchestrates a suite of specialized local LLMs to handle requests.

1. **System 1: Fast Reasoning & Triage**

   - **Model:** `qwen3:8b`
   - **Role:** Acts as the initial point of contact. It instantly interprets user intent, handles quick questions, and provides immediate suggestions. Its primary job is to classify the task and route it to the appropriate downstream system without delay.

2. **Task Router & Specialized Engines**

   - Based on the initial classification, the `Task Router` delegates the request to one of several specialized engines:
     - **Code Engine (`codellama:7b`):** Generates, refactors, and debugs code, producing rapid first-draft solutions.
     - **Conversational Agent (`gemma3:12b`):** Manages user-facing dialogue, crafts explanations, and generates documentation with the defined AuralA persona.
     - **Context Engine (`nomic-embed-text`):** A persistent engine that generates and queries vector embeddings, giving AuraIA a deep, semantic understanding of your project's codebase and history.

3. **System 2: Deep Reasoning & Verification**

   - **Model:** `deepseek-r1:8b`
   - **Role:** This is the analytical core. It validates the logic, correctness, and consistency of code generated by the `Code Engine`. It performs deeper reasoning to catch errors and ensure the final output is robust and reliable.

4. **Quality & Safety Pipeline**
   - **Safety Layer (`phi3:medium`):** Before any output is sent to the user, it is scanned for privacy violations, data leaks, and unsafe code patterns.
   - **Output Composer:** This final stage merges the rapid response from System 1 with the validated result from System 2, applies the `gemma3` persona for tone and clarity, and formats the final output for the IDE.

## Key Features

- **Advanced Cognitive Architecture:** A unique multi-layered system that mimics human thinking for both speed and accuracy.
- **Defined AI Persona:** A calm, supportive, and human-centric partner, not just a command-line tool.
- **Privacy-First Processing:** Leverages local LLMs via Ollama to ensure your code and data stay on your machine.
- **Sophisticated Model Routing:** Intelligently delegates tasks to the best model for the job, from quick intent classification to deep logical verification.
- **Deep Contextual Awareness:** Utilizes an embeddings-based `Context Engine` to maintain a rich understanding of your project.
- **End-to-End Quality Assurance:** A built-in verification and safety pipeline ensures all outputs are correct, safe, and polished.
- **Flexible and Extensible:** The modular architecture (FastAPI, `dependency-injector`) and optional dependencies (`crewai`) make it easy to extend and customize.

## RAG v2 configuration and observability

RAG v2 is available behind feature flags and integrates hybrid fusion retrieval, optional reranking, and lightweight observability.

- Flags (environment or settings):

  - `experimental_rag_v2_enabled`: Enable the RAG v2 pipeline
  - `hybrid_fusion_enabled`: Combine vector relevance with lexical (BM25 or proxy)
  - `fusion_weight_vector`: Weight for vector relevance (default 0.6)
  - `fusion_weight_bm25`: Weight for lexical relevance (default 0.4)
  - `reranker_model`: Optional Cross-Encoder model id; if unavailable, falls back
  - `relevance_threshold`: Threshold applied to the final score (0..1)
  - `rag_v2_code_top_k`: Number of code snippets to keep (default 8)

- Endpoints:

  - `GET /debug/rag_trace` — recent retrieval traces (per-document scores)
  - `GET /config/rag` — effective RAG configuration values

- Prometheus metrics:
  - `retrieval_docs_considered_total{stage="rag_v2"}`
  - `retrieval_docs_kept_total{stage="rag_v2"}`
  - `retrieval_topk_mean_fusion_score{stage="rag_v2"}`

Notes:

- BM25 is used if `rank_bm25` is installed; otherwise a lexical-overlap proxy is used.
- Cross-Encoder reranker is used if `sentence-transformers` CrossEncoder is available and `reranker_model` starts with `cross-encoder`.
- File watcher updates to embeddings are debounced to reduce redundant writes.

## Developer setup (backend) — Settings v2 + DI

This repo uses Pydantic Settings v2 for configuration and a dependency-injector container for wiring services. Here’s the quick-start for contributors.

### Environment

- Python 3.11 recommended. Create a virtual environment and install deps via the VS Code task:
  - Tasks: Run Task > Setup All (Install deps)
  - This provisions backend, frontend, and extension dependencies.
- Configuration is loaded from `backend/.env` automatically by `src/core/config.py`.
  - You can also set environment variables in your shell; env prefixes map to nested settings.

Common settings (env prefixes → nested classes):

- DB\_\* → `AppSettings.database` (e.g., `DB_REDIS_URL`)
- LLM\_\* → `AppSettings.llm` (e.g., `LLM_PROVIDER`, `LLM_OLLAMA_URL`, `LLM_DEFAULT_MODEL`, `LLM_ALLOW_CLOUD`, `LLM_ENABLE_CACHE`)
- CACHE\_\* → `AppSettings.cache`
- RATE*LIMIT*\* → `AppSettings.rate_limit`
- WORKSPACE\_\* → `AppSettings.workspace`
- MEMORY\_\* → `AppSettings.memory`
- EMBEDDINGS\_\* → `AppSettings.embeddings` (e.g., `EMBEDDINGS_PROVIDER`, `EMBEDDINGS_MODEL_NAME`, `EMBEDDINGS_OLLAMA_URL`)
- OBS\_\* → `AppSettings.observability` (e.g., `OBS_TRACE_LOG_PATH`, `OBS_TELEMETRY_MAX_METRICS`)
- MODE\_\* → `AppSettings.mode` (e.g., `MODE_DEFAULT_MODE=offline`)
- RAG*V2*\* → `AppSettings.rag_v2` (e.g., `RAG_V2_HYBRID_FUSION_ENABLED`)
- Feature flags on root `AppSettings`: `EXPERIMENTAL_RAG_V2_ENABLED`, `CONTEXT_ENABLED`

Files of interest:

- Settings (typed, Pydantic v2): `backend/src/core/config.py`
  - Access via `from src.core.config import get_settings` → returns cached `AppSettings`.
- DI Container (service wiring): `backend/src/core/container.py`
  - Exposes providers like `llm_manager`, `mode_manager`, `embeddings_service`, `llm_router`, `meta_orchestrator`, etc.
  - During app startup, the container is attached at `app.state.container` for optional access.

### Run, test, and quality gates

- Start everything for dev:
  - Tasks: Run Task > Start Dev Servers (runs backend API, frontend dev server, extension watch)
- Backend only:
  - Tasks: Run Task > Backend: Run API (Uvicorn)
- Tests:
  - Tasks: Run Task > Python: Run Tests (pytest, backend/tests)
  - Tasks: Run Task > Python: Test Coverage (optional HTML report)
- Lint/format:
  - Tasks: Run Task > Python: Lint with Flake8
  - Tasks: Run Task > Python: Format with Black
- Type check:
  - Tasks: Run Task > Python: Type Check (mypy)
  - Note: On some Windows setups mypy can intermittently show “Interrupted.” If that occurs, re-run or target critical modules (e.g., `src/core/config.py src/core/container.py`).

Troubleshooting tips:

- If the backend can’t see your env values, verify `backend/.env` exists and reload your window. The loader is initialized at import time in `src/core/config.py`.
- For RAG v2 observability routes, ensure `EXPERIMENTAL_RAG_V2_ENABLED=true` and check `/debug/rag_trace` and `/config/rag`.

## Multi-agent development flow

You can run multiple backend instances in parallel for isolation and load testing.

- VS Code tasks:
  - Tasks: Run Task > `Start Multi-Agent Backends (3x)` — launches Uvicorn on ports 8001, 8002, 8003
  - Each instance sets `APP_INSTANCE` (e.g., `agent-1`, `agent-2`, `agent-3`) and `PYTHONPATH=backend`
- PowerShell helper (Windows):

  - From repo root, run:

    ```powershell
    ./start-multi-agents.ps1 -Count 3 -BasePort 8001 -BindHost 127.0.0.1
    ```

  - Flags:
    - `-Count` number of instances (default 3)
    - `-BasePort` starting port (default 8001)
    - `-BindHost` host bind address (default 127.0.0.1)
    - `-NoReload` disable Uvicorn reload

Frontend/extension can be pointed at a specific backend port to exercise instances independently.

## CI overview and coverage gate

Our CI is split for speed and clarity:

- `Typecheck (mypy)`: runs on backend/\*\* changes with pip cache
- `CI` workflow:
  - `backend-lint`: Black + Flake8, YAML lint, Prometheus config validation
  - `backend-tests`: pytest with coverage and a coverage gate (`--cov-fail-under=60`)
  - `docker-build`: builds backend image, depends on tests
